# 05 — shadcn registry workflow

## Keep install metadata and website presentation metadata distinct

A shadcn registry item describes installation: `name`, `type`, `files`,
`dependencies`, `registryDependencies`, and related registry fields. The
website needs additional presentation data such as catalog category, tags,
previews, and editorial content.

The implemented project separates these two concerns completely:

- **Install data** lives in the per-item `registry.json` and is read by
  `src/lib/registry/items.ts`.
- **Presentation data** lives in `src/content/<category>/<slug>/metadata.ts`
  (and optional `content.tsx`), discovered with `import.meta.glob`.

Do not maintain duplicate title/tag/preview values by hand in multiple
unrelated files. See `docs/08-content-layer-and-adding-items.md` for the full
procedure. Earlier drafts of this pack suggested a `meta.catalog` block inside
`registry.json`; that shape is replaced by the content layer and should not be
re-introduced.

## Official registry types versus website categories

Use valid shadcn item types such as `registry:ui`, `registry:component`, and `registry:block`. Website categories are a separate abstraction; a route called `/collections/blocks` does not mean the item type should be a made-up `registry:blocks` value.

The shadcn registry format supports a root registry with `items` and/or `include`, and nested registry files can be used to organize a larger registry. When nested registries are included, file paths are resolved relative to the registry file that declares the item. The build pipeline should preserve that rule.

Official references:

- Registry JSON: https://ui.shadcn.com/docs/registry/registry-json
- Registry item JSON: https://ui.shadcn.com/docs/registry/registry-item-json
- Getting started: https://ui.shadcn.com/docs/registry/getting-started

## Recommended build flow

Adapt this to the scripts that already exist in the repository:

1. **Author** the item's install `registry.json` and its presentation
   `metadata.ts` (plus optional `content.tsx`), each in its own folder.
2. **Validate** the registry record (type, files, dependencies) and the
   presentation metadata (`validateItemMetadata` — run during tests).
3. **Discover** the catalog directly from `src/content/**/metadata.ts` with
   `import.meta.glob`; there is no separate manifest generation step.
4. **Check consistency**: each published catalog item maps to a real slug;
   source paths and preview assets exist; renderer keys are valid.
5. **Build and typecheck** the Next.js application.

Generated JSON should be treated as generated output if it is generated by a
script. Do not manually patch it and expect the changes to survive
regeneration.

## Existing per-item metadata folders

The repository keeps per-item `registry/ui/<item>/registry.json` files,
aggregated by the manual `include` list in `src/registry/ui/registry.json`
(shadcn's `include` cannot glob, so that list stays a one-line manual edit —
see `docs/08`). The website catalog is NOT generated from those files; it is
discovered from `src/content/`. Keep the two concerns separate and validate
both rather than mixing them.

## Avoid two sources of truth

Do not separately hand-author one version of an item's title and tags in the registry metadata and a different version in a hardcoded TypeScript list. Prefer a generation step, typed manifest, or keyed supplemental metadata so every published item resolves deterministically.
