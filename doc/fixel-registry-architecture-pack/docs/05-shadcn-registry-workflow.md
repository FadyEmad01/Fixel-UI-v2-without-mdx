# 05 — shadcn registry workflow

## Keep install metadata and website presentation metadata distinct

A shadcn registry item describes installation: `name`, `type`, `files`, `dependencies`, `registryDependencies`, and related registry fields. The website needs additional presentation data such as catalog category, tags, and preview media.

A practical pattern is to put site-specific values under the registry item's extensible `meta` field, for example `meta.catalog`, then normalize that data into a website `CatalogItem` manifest. Another valid pattern is a separate catalog manifest keyed by item name. Prefer whichever option fits the current scripts; do not maintain duplicate title/tag/preview values by hand in multiple unrelated files.

Example of `meta.catalog`:

```json
{
  "meta": {
    "catalog": {
      "category": "ui",
      "tags": ["motion", "button", "hover"],
      "preview": {
        "renderer": "video",
        "src": "/previews/animated-button.mp4",
        "poster": "/previews/animated-button.jpg"
      }
    }
  }
}
```

The full example item is in `examples/registry/ui/animated-button/registry.json`.

## Official registry types versus website categories

Use valid shadcn item types such as `registry:ui`, `registry:component`, and `registry:block`. Website categories are a separate abstraction; a route called `/collections/blocks` does not mean the item type should be a made-up `registry:blocks` value.

The shadcn registry format supports a root registry with `items` and/or `include`, and nested registry files can be used to organize a larger registry. When nested registries are included, file paths are resolved relative to the registry file that declares the item. The build pipeline should preserve that rule.

Official references:

- Registry JSON: https://ui.shadcn.com/docs/registry/registry-json
- Registry item JSON: https://ui.shadcn.com/docs/registry/registry-item-json
- Getting started: https://ui.shadcn.com/docs/registry/getting-started

## Recommended build flow

Adapt this to the scripts that already exist in the repository:

1. **Author** item files and their install/catalog metadata in one predictable location.
2. **Validate** required registry fields, category values, tags, preview configuration, dependencies, and source paths.
3. **Generate/normalize** the official shadcn registry input/output using the existing build process.
4. **Generate the website manifest** from the same canonical item metadata.
5. **Check consistency**: each published catalog item maps to a valid item name; source paths and preview assets exist; renderer keys are valid.
6. **Build and typecheck** the Next.js application.

Generated JSON should be treated as generated output if it is generated by a script. Do not manually patch it and expect the changes to survive regeneration.

## Existing per-item metadata folders

If the repository already has per-item files such as `registry/ui/<item>/registry.json`, preserve that convention if it is working. Add or update the generator that aggregates per-item metadata into the registry structure expected by shadcn and emits the website catalog manifest. Do not assume that the official `include` field automatically includes an arbitrary per-item JSON file: `include` expects registry documents in the supported registry format.

Keep file paths consistent with the current generator's path rules. A nested registry's paths may be relative to that nested registry file; a custom per-item manifest may instead define root-relative paths and normalize them during generation. Document and validate the rule rather than mixing both styles.

## Avoid two sources of truth

Do not separately hand-author one version of an item's title and tags in the registry metadata and a different version in a hardcoded TypeScript list. Prefer a generation step, typed manifest, or keyed supplemental metadata so every published item resolves deterministically.
